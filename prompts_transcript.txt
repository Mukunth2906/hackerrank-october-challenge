Problem statement: Northstar Shop lost $2.4M after a "deleted" customer reappeared.
Build an AI deletion audit agent that reads the dataset files (requests, identities,

[ASSISTANT ANALYSIS & DESIGN]
- The problem is a forensic audit and planning task on frozen evidence, not live
  DB synchronization. Sync matters only as something to detect (active flows that
  recreate data) and disable in the plan.
- About 80% of the work is deterministic logic. An LLM or VLM should only convert
  unstructured evidence (PDF, PNG) into facts, and classify ambiguous request text.
- Pipeline: intent gate -> identity resolver -> evidence index (cached) ->
  state reconstruction at audit_at -> policy engine -> gap analysis ->
  step planner and sorter -> schema validator.
- Identity: resolve current and historical emails, email hashes, phone and user_id.
  Normalize case before matching.
- Status rule: COMPLETE only if there are no remaining records, no active flow,
  no restore risk, and retained records are still present.
- Sort key: (phase, operation rank, system_id, resource_id), with step_no renumbered from 1.
- Cost plan: extract each evidence file once, cache it, and call a model only for
  ambiguous requests and images/PDFs.
- Evaluation plan: diff against the sample output, build a confusion matrix, run
  step-level and sequence metrics, add at least 3 custom cases, and log failures and fixes.
- Failure modes: trusting reported_status or "SUCCESS" logs, ignoring audit_at,
  missing historical emails, deleting tombstones instead of redacting them,
  deleting retained records, missing active flows and restore risks, wrong ordering,
  missing evidence IDs.
- Build order: schema validator, identity resolver, parsers, state reconstructor,
  planner and sorter, run on the sample, then add VLM/OCR and the intent classifier,
  then the reports.

TURN 2: Design Thesis (SEANCE: Stateful Evidence-And-Claim Engine)
--------------------------------------------------------------------------------
[USER PROMPT]
"It should be unique. The same Claude might give the same answer to 50,000 other people. Think like a great project master."

[ASSISTANT: DESIGN THESIS (SEANCE)]
Name: Stateful Evidence-And-Claim Engine.
Thesis: Northstar failed by trusting claims over observations, so the system separates the two and proves absence.
1. Claim vs Observation ledger: Snapshot/file contents are observations (high trust).
   Activity-log "SUCCESS" and reported_status are claims (low trust). A ghost is a disagreement between the two.
2. Temporal identity graph with fixpoint expansion over emails, hashes, phones, and user_id.
3. Resurrection graph: Active flows and restore paths are edges. Report only flows that touch this user.
4. Closed-loop plan simulation (digital twin): Apply the plan, re-audit, and require COMPLETE with retained records intact.
   This catches both under-fix and over-delete.
5. Ghost-injection evaluation: Take clean cases, inject one ghost of a known type, and assert the status flips and
   the step count is correct. Report recall per ghost type.
6. Uncertainty-routed LLM: Deterministic code first. The LLM/VLM is called only for residual uncertainty,
   with schema-constrained output, double-read consensus and file-hash caching.
7. Reverse-engineer generator conventions from sample_output.csv into config, not per-case answers.
- Invariants: sorted steps; consecutive step_no; COMPLETE is verification-only with evidence IDs;
  NOT_APPLICABLE is exactly []; every finding has one remediation and one verification;
  retained resources are verified PRESENT, never deleted; 518 rows sorted by case_id.
- Phases: data autopsy, deterministic core, twin and invariants, ghost injector and metrics, VLM and classifier, reports and README.
- Token example: naive ~10.4M tokens vs cached ~0.5M.

# Review of that exploration log

The Antigravity log is a good start, but it stops one step before the part that decides your score. It confirms the shape of the data and the sort order. It never shows how a case maps to specific resources inside the evidence files, and that mapping is where most of the points are.

## What it confirms (matches my earlier read)

- **Counts agree.** The report has 518 requests (case_33 to case_550), 32 samples, 850 identities, 306 audit rows, 4,011 activities, 15 rules and 94 evidence files. The format split (24 sql, 28 json, 1 txt, 26 log, 4 pdf, 11 png) sums to 94 and matches the manifest.
- **The 10 non-deletion cases are the same ones.** They are case_533 to case_542.
- **The sort invariants hold on all 32 samples.**
- **Evidence is the ground truth.** The `DELETE SUCCESS` claim for account_005 is contradicted by the failover replica in evidence_54.

## What it misses or leaves open

1. **The 12 `LINK_RESOURCE_IDENTITY` activities (4000 to 4011).** The report never mentions them. They are the only place the activity log ties a resource to an email and user_id. Their timestamps equal the matching image's `captured_at` plus 7m01s, so these 12 are the image and PDF cases. This is a strong shortcut: the PNG/PDF cases may not need free-form OCR at all, only a check against a known resource and user.
2. **The within-tie sort is untested.** "system_id then resource_id ascending" was confirmed only on samples where no two steps share an operation and a system. Whether `search_898` sorts before `search_1308` (numeric or string) is unknown. Plain string order puts `search_1308` first. Test both on a fixture and keep whichever matches any sample row that has such a pair, otherwise default to string.
3. **Time travel and duplicate users.** Ingrid Dahl appears in case_52 (audit 06-19) and case_33 (audit 07-19). She has two exports, and the second is linked on 07-18. The report doesn't mention this, but it decides case_52 versus case_33.
4. **Future files.** Files captured after `audit_at` must be ignored. For example, the 08-22 restore of backup_9287 into search_4882 is invisible to a case audited 04-30.
5. **The "100% resolve" claim.** It may rest on a lowercase join. Walk chains by `(user_id, event_time)` pairs and not by row adjacency, because audit_234 (hash) comes before audit_235 (email) for the same event.
6. **No hash check.** Nobody verified that `email_hash = sha256(lower(email))`. Run one quick Python check on 5 rows before relying on it for matching tombstones and secondary identifiers.
7. **The PDFs and PNGs.** The report found only `pypdfium2` and no OCR (`pytesseract`, `easyocr` and `paddleocr` all came up empty). The images were viewed by the IDE's own model, which won't exist at submission time. Your pipeline needs a VLM call with caching per file, and the usage report must count those calls.
